## A. 截屏时 OCRFlow 被激活 → 一串下游补丁

**根因**：旧流程里截屏会 `NSApp.activate()`，被截的窗口因此变成后台窗口（标题栏变浅），之后又把激活交还回去（窗口再变深）。同一个窗口在截屏过程中前后两种样子，拼接和比较就对不上，于是在下游一处处加容差。

| # | 补丁 | 位置 |
|---|---|---|
| A1 | 批量拼接时，上下固定边取"第二小"而不是所有配对共有的值，理由是"第一张在选择时截的，标题栏更浅" | `ScrollStitcher.swift:88-101` |
| A2 | 实时拼接时，第一帧"原地变化"（"窗口在截屏开始时到了前台"）就把它换成新的起点 | `LiveStitcher.swift:77-95` |
| A3 | `sameRows` 容差 <4，理由之一是"窗口进出前台时颜色深浅变化" | `ScrollStitcher.swift:271-276` |
| A4 | Stage Manager 下交还激活后固定等 150 ms | 已在未提交改动里删掉 ✅ |
| A5 | 弹权限/错误提示用 `NSAlert.runModal()`，它必须激活 OCRFlow，于是用 `OwnWindows.whileModal` 先把自己的窗口藏起来、事后再放回去 | `ScreenCapture.swift:80,91`【冲突】、`StepPlayer.swift:82`、`OwnWindows.swift:38-45` |
| A6 | 跑宏前 `OwnWindows.tuck()` 把主窗口藏起来"别挡点击"。但从 a277dbf 起，每一步执行前都会先把该步的 app 调到前台，这个隐藏多半已经多余（副作用：跑宏时主窗口会消失） | `OCRViewModel+Macros.swift:46` |

**根本修法**：
- 那边的会话落地"全程不激活"后，删掉 A1、A2 里专门为激活加的分支，A3 只留"标题栏透出底下内容"这个理由，再用真实 app 重新跑长截图测试。
- A5：提示改用已有的不激活面板（`ResultChoice.tell` 那种 HUD），不再走模态 NSAlert，`whileModal` 随之删除。
- A6：去掉 tuck，从主窗口跑一个宏验证。没问题就把 `OwnWindows.tuck/restore` 一起删掉。

把握：高（A1/A2/A5），中（A6，要实测）。

## B. 窗口截图尺寸"偶尔差一个点"：同一个原因叠了三层容差

| 层 | 位置 |
|---|---|
| 1. 窗口改用 `window.frame.size`，理由是"filter 报的尺寸会晃" | `ScreenGrabber.swift:54-58` |
| 2. `like:`：与上一张相差 ±4 px 以内就强行用上一张的尺寸 | `ScreenGrabber.swift:98-102` |
| 3. 拼接时接受大 ≤4 px 的图，再裁掉多出来的 | `ScrollStitcher.swift:52-57` |
| （配套）宏运行时沿用录制时的尺寸 | `MacroPlayer.swift:193,198`、`OCRViewModel+Macros.swift` |

**根因还没找到**：一直没弄清是哪个值在晃。候选有：`filter.contentRect` 带不带阴影、窗口动画进行中的小数坐标、跨不同缩放比显示器时的 `pointPixelScale`、`.rounded()` 的取整方向。区域截图这边，未提交改动里的 `CGRect(draggedFrom:to:)` 已经对齐到整点，算是从根上解决了。

**根本修法**：加日志，连续截同一个窗口记下每个候选值，找出晃动的来源并在源头取整或改用稳定的值，然后删掉第 2、3 层。

把握：中（要先测量）。

## C. 用固定延时代替"等到条件成立"

| 补丁 | 位置 | 后果 / 根本修法 |

| 启动 app 后固定睡 2 s，只找一次窗口 | `MacroPlayer.swift:259-263` | 慢的 app 2 s 内出不来窗口，就会被报成"找不到 app"。改成在期限内等窗口出现 |

## E. Auto Scroll 按钮"滚轮穿透"用 0.4 s 计时器切换 `ignoresMouseEvents`

`CaptureBar.swift:273-316`【冲突】

- **实际问题**：按钮上的第一下滚轮被吞掉，没有传给页面；停止滚动后 0.4 s 内点按钮，点击会穿透到下面的页面（可能点中链接）。
- **根因**：区域中间有一个接收点击的窗口，挡住了要滚动的内容。用计时器猜"用户是不是还在滚"，属于补丁。
- **根本修法**：面板始终 `ignoresMouseEvents = true`。按钮上的点击由已有的事件 tap（`ScrollingCapture.watchTheUser`，本来就在拦截点击）按按钮的位置识别并吞掉。滚轮从此永远直达页面。

把握：中高。

## F. 录制时"第一次点进别的 app 不算一步"

`MacroRecorder.swift:225-235`【冲突】

- **根因**：从 OCRFlow 自己的窗口开始录制时，OCRFlow 在前台，第一次点击其实只是激活另一个 app。
- **问题**：这是靠猜的。能接受第一次点击的 app（`acceptsFirstMouse`）会真的响应这次点击，这一步就丢了。
- **方向**：开始录制时就把前台交还给原来的 app，或者只允许从不激活 OCRFlow 的入口（菜单栏、浮动按钮、快捷键）开始录制，让"第一次点击"不再特殊。这条需要你定方向。

把握：低到中。

# 处理结果（2026-11-01，另一个会话的改动落地之后）

## 另一个会话的改动（"截屏全程不激活"），同样审查过

- **截屏选择时每帧读一次指针**（`CaptureOverlay` 的 `Ticker`）：不算补丁。截屏进入实时状态后，指针在别的 app 的窗口上，移动事件发给那个 app，不发给 OCRFlow。而且画出来的指针本来就要逐帧跟上。原注释的理由（"不可靠"）太含糊，已改成真实原因。
- **自己画指针**、**按 app 排除截屏内容**、**按键"认领"可叠加**、**同级面板点击会被调到前面，所以 marks 用 screenSaver+1**：理由都成立，不是补丁。
- **长截图开始前可以调整区域，调整后用 `generation` 丢掉旧流程的帧**：旧的帧流停止后，可能还有已经排进主线程的帧，这是正确的做法。

## 每条的处理

| 条目 | 处理 |
|---|---|
| A1 批量拼接取"第二小"的边 | **保留，改了注释**。截屏不再激活 OCRFlow 后，剩下的真实情况是：第一张是录制时截的，那时窗口可能在后台。用一对图的偏差容忍一个例外，属于稳健估计，不是补丁 |
| A2 实时拼接"原地变化" | **保留，改了注释**。实时截屏时点击会落到页面上，用户点一下窗口，它就会到前台、重画选中状态，这个情况是真实存在的 |
| A3 `sameRows` 容差 | 保留（标题栏会透出底下滚过的内容） |
| A5 模态 NSAlert + 藏窗口 | **已修**。权限和错误提示改用不激活的 HUD（`ResultChoice.tell` 增加了一个操作按钮），`OwnWindows.whileModal` 已删除 |
| A6 跑宏前藏窗口 | **保留，改了注释**。这不是多余的：一步截取的是屏幕区域时，OCRFlow 的主窗口会出现在截图里。藏起来，屏幕才和录制时一样 |
| B 尺寸三层容差 | **找到根因并修了**。跑宏时，窗口位置或大小相差 ≤2 点就不放回录制时的位置（`moved > 2`），于是截出来的图差一两个点，再靠 `like:` 把图**缩放**回原尺寸来凑。现在：差一点也放回去，并等窗口真的到位；`like:` 和 `frameSize` 删除（截图不再被缩放）；批量拼接只用尺寸相同的帧（取出现最多的尺寸），不再裁掉多出的 4 px |
| C 固定延时 | **已修**。启动 app 后等它的窗口出现（最多 20 s）；移动窗口后等它到位；打开网址后先等 app 到前台，再等它的窗口变化并停下；宏里的长截图从第一帧开始，结尾等画面停下（帧流只在画面变化时才发帧）；实时测试里等界面出现的固定延时换成了条件等待（还剩一部分模拟手速的间隔） |
| D 浮动按钮轮询 | **已修**。改用 `.activeAlways` 的跟踪区域（move/enter/exit），离开后宽限 0.4 s 再收起 |
| E 滚轮穿透计时器 | **已修**。Auto Scroll 按钮的面板始终不接收鼠标，滚轮总能到达页面；点按钮由长截图本来就有的事件 tap 识别并吞掉，`WheelThroughPanel` 已删除 |
| F 录制时第一下点击 | **已修根因**。在 OCRFlow 窗口里开始录制时，OCRFlow 把前台交还给用户之前所在的 app（见下面的"验证"），用户在那里的第一下点击就是普通点击。规则只留一种情况：第一下点进的是另一个 app，这时它确实只是把那个 app 调到前台 |
| G 版面碎片框按文字去重 | **保留**。几何阶段已和 PaddleX 一致（NMS + 包含关系合并），碎片框是模型本身的输出，代码里没有更上游的根因可修，文字是唯一能用来判断的信号 |
| H 兼容代码 | **已删** `settleEquivalentReadings`，翻译那处去掉了"earlier build"的说法（剩下的逻辑仍然需要：系统语言推出来的默认值） |

## 验证

- 单元测试：除实时测试外 92 个全部通过，包括新加的"只拼同尺寸的图"。
- 自动化实时测试结果不可靠（第一轮被系统的录屏确认框干扰，第二轮中途被打断）。之后改为由 Haiku 在真实的 app 里手动点击测试（开着 Stage Manager，前台是文本编辑）：
  - 截屏：整个过程中 OCRFlow 没有到前台，按 Escape 退出后前台仍是文本编辑。
  - 长截图：鼠标在 Auto Scroll 按钮上时，滚轮能滚动下面的页面；点一下按钮开始自动滚动，指针不动；动一下鼠标就停止。从文件顶部一直滚到末尾，预览每秒都在变长，没有出现"太快了"的提示。
  - 浮动按钮：悬停时展开，慢慢移过各个选项不会收起，移开后约 1 秒内收起，前台一直是文本编辑。
  - 录制：**第一轮手动测试发现 F 的修法不对**。在 OCRFlow 窗口里开始录制时，`NSApp.deactivate()` 并不会把前台交出去（macOS 14 起激活是协作式的，只"退后"的 app 仍然留在前台），于是第一下点击被当成"把 app 调到前台"而丢掉了。改为：从启动起记住用户最后所在的、不是 OCRFlow 的 app，开始录制时用 `yieldActivation` + `activate(from:)` 把前台交给它（跑宏时调 app 到前台用的也是这一套）。改后复测：从文件菜单开始录制，约 1 秒内文本编辑回到前台；从浮动按钮开始录制，文本编辑一直在前台。两种方式都录到了"点击"和"Page Down"两步。
  - 跑宏：文本编辑回到前台，翻了一页，没有报错。
